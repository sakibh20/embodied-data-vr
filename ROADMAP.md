## Phase F — Post-simulator regression fix + run-mode settings (2026-09-06)
- [x] **M19. Fix walk-value offset & broken activation-range gating (introduced after the XR Interaction Simulator setup).** Root cause: `WalkValueDriver`/`SessionController` each resolved "the head" transform exactly once, in `Awake()`, via a `Camera.main` / `XRSettings.isDeviceActive` guess. Two problems made that guess unreliable once a second rig existed: (1) both `XR Origin (XR Rig)` and the spare `XR Origin (VR)` have their camera tagged `MainCamera`, so `Camera.main` is ambiguous whenever more than one is active; (2) the one-shot Awake resolution goes stale if the active rig changes after that (e.g. toggling modes without stopping Play). Both symptoms — cues reacting with a constant offset, and the on-walk activation region misbehaving — came from the same stale/wrong transform being read every frame. Fix: added `PlayerRig` (a live, never-cached pointer to the current head) and `SessionBootstrap` (`[DefaultExecutionOrder(-100)]`), which now **explicitly** activates exactly one rig for the chosen `RunType` and assigns `PlayerRig.Head` directly (no tag/heuristic guessing). `WalkValueDriver.Update()` and `SessionController.Update()` now read `PlayerRig.Head` fresh every frame, falling back to the old heuristic only if nothing set it (e.g. an ad-hoc scene without a Bootstrap). Verified in Play mode for both Desktop and Simulator: exactly one rig active, `PlayerRig.Head` resolves to the transform actually being moved, and `PathSampler` distance/region math is offset-free (checked directly against known walk-corridor positions).
- [x] **M20. RunSettings + SessionBootstrap.** Added `RunSettings` (ScriptableObject, `Assets/ScriptableObjects/RunSettings.asset`) holding `audioMode` and `runType` (Desktop/Simulator/VR) — edited directly on the asset for now. `SessionBootstrap` in `Assets/Scenes/Experiment.unity` reads it at startup, activates exactly one rig for the chosen `runType`, applies the audio mode, and starts the session automatically: open the scene and press Play, nothing else needed. (A separate `Init.unity` scene with a Start Session button was tried as an entry point and then removed as unnecessary — `SessionBootstrap` alone covers it.) This also removes the old manual "remember to enable/disable the right GameObjects before pressing Play" step — `RunSettings` is now the single source of truth for which rig is active.
- [x] **M21. Fix the deeper "still not synced / offset outside the graph" bug found right after M19.** After the M19 fix, the offset symptom persisted: cues still fired well past the true end of the walk corridor and the retrace felt out of sync with the data. Root cause was a *second*, independent bug in `GraphManager.ConfigureSampler()`: it measured the per-point walk segment as the **Euclidean distance** between the first two spawned dots (`Vector3.Distance(dot0, dot1)`), but a dot's position is offset **laterally** (value maps to lateral floor offset, not the walk axis) — so that distance is inflated by the value swing between adjacent points, which inflated `PathSampler.TotalLength` and every distance/region computation built on it. Fixed by projecting onto the walk axis instead: `segment = Vector3.Dot(lastDot - firstDot, walkDir) / (pointCount - 1)`. Verified live (after a full Stop/Play — **this project has Reload Domain disabled**, so a script recompile while already in Play mode does not take effect until you stop and re-enter Play; a same-session recompile can look like "the fix did nothing" when it's actually still running old code): `PathSampler.TotalLength` now reads exactly `3.0` (matching `GraphManager`'s `targetWalkLength`), and positions 0.6 m/3 m past the true graph end correctly report `inRegion = False`. User-confirmed in-session: "perfect, in sync now."
- [x] **M22. Recall/option UI overflow fix + prefab-based UI architecture + configurable recall input mode.** `SessionUI` previously built its entire world-space canvas from scratch in code (`new GameObject(...)` for the canvas, panel, title, body, and every button) — nothing was editable in the Unity Editor, and a `VerticalLayoutGroup` with `childControlHeight=false` left buttons at Unity's default 100×100 rect size regardless of their `LayoutElement`, so a full set of options could run past the panel's edge ("options going out of the screen"). Replaced with three authored prefabs under `Assets/Prefabs/UI/`: **`SessionCanvas.prefab`** (world-space Canvas + fixed Title/Body header + a `ScrollRect`/`RectMask2D`/`Content` scrollable area, via the new `SessionCanvasView` component), **`SessionOptionButton.prefab`** (a button + label, via `SessionOptionButton`), and **`SessionAnswerInput.prefab`** (a `TMP_InputField` + unit label + Submit button, via `SessionAnswerInput`). `SessionUI.cs` now `Instantiate()`s these at runtime and only sets text/callbacks — the whole look (colors, fonts, spacing, button height) is editable directly on the prefabs in the Editor, and the scrollable content area means any future overflow (more options, longer prompts) scrolls instead of spilling past the panel. Also added a **configurable recall input mode**: `RunSettings.recallInputMode` (`MultipleChoice` / `TextEntry`) — `RecallQuestion` (StudyTypes.cs) now always carries both the 4-option MCQ representation and the raw `answerValue`/`unit`, and a new `StudyConfig` static (set by `SessionBootstrap`, mirroring `PlayerRig`) tells `SessionUI` which to render. `SessionController.AnswerCurrentQuestionText(string)` scores a typed value against `answerValue` using the same display rounding as the MCQ options. Verified live in both modes: MCQ renders 4 buttons at their intended 68px height (no overflow, well within the scrollable viewport), and TextEntry renders the input box, scores a correct/typed answer, and advances through all 4 questions correctly.
- [x] **M23. Replace the plain "Spark" sphere with a proper electric-orb shader/material.** `SparkObject.prefab` (used by the Representative and MismatchNonRep/semantic-visual conditions, spawned up to 100-at-once by `DensityController`) previously used a stock `Universal Render Pipeline/Lit` material (`Spark.mat`) — just a flat orange sphere with mild HDR emission, no motion, no "electric" read. Wrote a hand-authored URP Unlit shader, `Assets/Shaders/ElectricOrb.shader`, and a new material `Assets/Materials/ElectricOrb.mat` (GPU Instancing on) now assigned on the prefab: a Fresnel rim (bright cyan edge, deep blue core), two crossing animated ridged-noise layers forming thin crackling filament/lightning veins across the surface, and a slow brightness pulse — all per-instance-desynced for free via a hash of each object's world position (no per-instance script/MaterialPropertyBlock work, so it stays cheap at 100 instances in VR: single Unlit pass, no textures, no per-object lights). Every visual parameter (core/edge color, brightness, Fresnel power, arc noise scale/speed/sharpness/intensity, pulse speed/amount) is an exposed material property, tunable directly in the Inspector with no shader edits. Verified live in Play mode (Representative condition, density driven to 100 instances): compiles clean, renders correctly at both close range and normal room-viewing distance, no console errors.
